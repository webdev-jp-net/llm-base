# 自己改善ルール

このプロジェクトを「実行するたびに賢くなるシステム」として運用するためのルール。
4つの仕組みで構成される。

**記録の正本は`_llm-memories/`直下の3ファイル**（`state.md` / `lessons.md` / `episodes.md`）。
実行記録をこれ以外の場所に二重保存しない。
読むときはRead、更新するときはEditで変更箇所だけを置換する。
`old_string`は一致が1箇所になるよう指定する。必要に応じて見出しや前後の行を含める。
Writeは全体上書きで1行の更新でも全文を出力し直すため、新規作成のときだけ使う。
この3ファイルはバージョン管理の対象外で、`_llm-memories/templates/`のみがGit管理される。

| 仕組み            | 置き場                                                   | 目的                           |
| ----------------- | -------------------------------------------------------- | ------------------------------ |
| STATE             | `_llm-memories/state.md`                                 | 進捗記録・中断からの再開       |
| Memory            | `_llm-memories/lessons.md` / `_llm-memories/episodes.md` | 失敗の再発防止・成功の再利用   |
| Verification Loop | 本ファイル                                               | 出力品質の独立検証と自動修正   |
| Router            | 本ファイル                                               | タスク種別ごとの実行者振り分け |

`state`/`lessons`/`episodes`は**実行の記録**（毎回変わる事実）。仕様や設計の知識はここに書かず、`_llm-docs/`に置く。

## 初回セットアップ（記録が存在しないとき）

`_llm-memories/`直下に`state.md`/`lessons.md`/`episodes.md`が揃っていないリポジトリでは、着手前に`_llm-memories/templates/`の同名ファイルをコピーして作成してから始める（ユーザーに問い返さず初期化する）。
記録が1つも無い状態では、read-gateが`_llm-memories/`配下の作成だけを通すため、先に作らないと他の変更操作に進めない。

## STATE運用ルール

### 読むタイミング（必須）

- セッション開始時、core_rules.mdの「状態・記憶の確認」の一部として`_llm-memories/state.md`を読む
- ステータスが`in_progress`なら「前回の続き」がある。チェックポイントの`next_action`から再開することをユーザーに提案する

### 更新タイミング（必須）

- タスク開始時: メタデータ・goal・フェーズ一覧を記入し、ステータスを`in_progress`に
- フェーズ完了ごと: フェーズにチェック・チェックポイント（`next_action`と成果物パス）を更新
- エラー発生時: `errors_encountered`に追記（同時に`lessons`にも記録）
- タスク完了時: ステータスを`completed`にし、引き継ぎメモを書く

### 原則

- チェックポイントは「このメモリだけ読めば再開できる」粒度で書く
- 長時間・複数フェーズのタスクほど更新頻度を上げる（目安: 意味のある成果物ができるたび）

## Memory運用ルール

### タスク着手前（必須）

- `_llm-memories/lessons.md`の関連カテゴリを確認し、既知の失敗パターンを事前回避する
- `_llm-memories/episodes.md`で類似タスクの成功アプローチを確認する

### タスク完了後（必須）

- `episodes`に1行追加（タスクタイプ・結果・有効だったアプローチ）
- 失敗・手戻りがあった場合は`lessons`に教訓を追加。既存教訓の再発なら発生回数を増やす

### スキル化（漸進的改善）

- 同種タスクの成功が3回に達したら、`episodes`の「スキル化候補」に登録し、ユーザーにスキル化を提案する
- 承認後、`.claude/skills/`に既存スキルの形式（frontmatter+手順書）で作成する
- 勝手にスキルを作成しない（core_rules.mdの承認原則に従う）

## Verification Loop（検証ループ）

### 原則

- 重要な成果物は、**作成した者と別の視点**で検証する（同じ文脈は同じバイアスを持つ）
- 検証は「良い/悪い」でなく基準に対する合否で判定する
- 結果は`_llm-memories/state.md`の「検証結果ログ」に必ず記録する

### 検証者の選択

| 成果物               | 検証者                                                     |
| -------------------- | ---------------------------------------------------------- |
| コード               | `code-review`スキル（Codex CLI＝独立モデル）               |
| ドキュメント・仕様書 | `doc-review`スキル（Codex CLI）                            |
| 上記以外             | サブエージェント（新しいコンテキストで基準に照らして評価） |

### 検証基準（品質ゲート）

| 成果物       | 基準                                                                            |
| ------------ | ------------------------------------------------------------------------------- |
| コード       | lint/型チェック通過・ロジック正当性・セキュリティ・既存パターン準拠             |
| ドキュメント | 事実正確性（仕様書との一致）・論理整合・要求項目の網羅・dictionary.mdの用語準拠 |
| UI           | 表示崩れなし・仕様通りの挙動・レスポンシブ確認                                  |

品質ゲートの目安: 草稿=指摘があっても可 / レビュー依頼前=重大指摘ゼロ / PR作成前=全指摘解消。

### ループ手順

- 成果物を作成する
- 上記の検証者に検証させる
- **合格** → `state`に記録して次フェーズへ。`episodes`に成功を記録
- **不合格** → 指摘を具体的な修正指示に変換して修正・再検証（最大3回）
- 3回で合格しない場合 → 作業を止め、最良版と問題点を添えてユーザーにエスカレーション（無限リトライ禁止）

### エスカレーション条件（自動化してはいけない判断）

- 再試行3回超過 / 未知のエラー / 仕様の空白の発見 / UI・UXデザインの変更判断 /
  データ削除等の破壊的操作 / コミット・PR作成（既存ルール通り承認必須）

## Router（実行者の振り分け）

タスク種別ごとに最適な実行者を選ぶ。すべてをメインセッションで実行しない。

| タスク種別                                                     | 実行者                            | 理由                                                                 |
| -------------------------------------------------------------- | --------------------------------- | -------------------------------------------------------------------- |
| シンボルのピンポイント照会（定義・参照・依存の特定）           | Serena検索ツール（find_symbol等） | 速く正確。LSPベース                                                  |
| 広域調査（多数ファイルを読む必要があるが、欲しいのは結論だけ） | サブエージェント（Explore）       | 大量読み込みを別コンテキストに隔離し、メインのコンテキスト消費を防ぐ |
| 実装・編集                                                     | メインセッション                  | 承認フロー・文脈の一貫性                                             |
| コードレビュー                                                 | Codex CLI（code-reviewスキル）    | 独立モデルによる検証                                                 |
| ドキュメントレビュー                                           | Codex CLI（doc-reviewスキル）     | 同上                                                                 |
| 定型作業（ブランチ後始末等）                                   | 該当スキル                        | 検証済み手順の再利用                                                 |
| 単純な変換・整形                                               | メインセッションで即実行          | 委任コストの方が高い                                                 |

探索の使い分けの軸は「リポジトリ内か外か」ではなく**照会の性質**：
答えの場所が特定できる照会はSerena、広く読んで要約が欲しい調査はサブエージェント。

### 振り分けの自己最適化

- 振り分けが失敗した（不適切な実行者を選んだ）場合は`lessons`に記録する
- `episodes`で特定の実行者の成功率が高いと分かったら、この表の更新を提案する

## 最小運用（迷ったらこれだけ）

- 開始時: `_llm-memories/state.md`と`_llm-memories/lessons.md`を読む
- 完了時: `state.md`と`episodes.md`を更新する
- 重要成果物: 別の視点で検証してから完了とする
